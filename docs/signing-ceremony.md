# The agent's release signing key

Written 2026-08-19. **This is a human ceremony and not a task for an agent.**

## Why it has to happen before a phone is enrolled

The provisioning QR carries the SHA-256 of the **signing certificate**, and
Android installs the agent only if the download matches it. That is the whole
reason the download can be unauthenticated.

The consequence is the part worth reading twice: an Android app is identified by
its signing certificate for as long as it is installed, and a Device Owner
cannot be replaced by an APK signed with a different key. So

- **changing the signing key later means factory-resetting every enrolled
  device**, and
- losing the key means no enrolled device can ever be updated again.

Today `check.agent-android.yml` produces a debug-signed APK. Its certificate
checksum was `sFwqKgjnKGoge3NeLs3_WsiUni6Dzxe24CQuX4KYnYE` on 2026-08-19. The
debug keystore is auto-generated by the SDK on the mac mini, is not backed up,
and is recreated if deleted - so enrolling against it buys a wipe later. Doing
this ceremony first makes every future agent update a silent install over the
top instead.

## Residual risk, accepted 2026-08-23, re-based 2026-08-28

Signing runs on a self-hosted runner that also executes the checked-out tree's
own build logic. Gating the secrets by event stops a run reading the key during
its own run; it does not isolate the machine. Code that executes there can
persist outside the checkout - a Gradle init script in `~/.gradle`, a replaced
tool on `PATH` - and collect the key on a later main build, and the certificate
pin cannot detect that: a build signed with the genuinely stolen key matches the
pin by definition.

This was accepted on the grounds that the only writers are the operator and
agents under the operator's control, **on a private repository with no external
contributors** - a precondition that expires the moment anyone else can open a
pull request here.

**What changed on 2026-08-28.** Rather than let that precondition expire on the
day the repository goes public, both self-hosted workflows now enforce it
directly. `check.agent-android.yml` and `check.server.yml` carry a job-level
condition admitting `pull_request` events only when the head repository IS this
repository:

    if: >-
      github.event_name != 'pull_request'
      || github.event.pull_request.head.repo.full_name == github.repository

A fork pull request therefore schedules nothing on the runner - its checks
report as skipped. Only a branch in this repository reaches the machine, and
only someone with write access can push one. So the set of code that executes
next to the signing key is unchanged by the repository becoming public, and the
acceptance above now rests on a condition the workflows enforce rather than on
the repository's visibility.

**The condition is the control.** If it is ever relaxed - a `pull_request_target`
trigger, a manual approval that lets fork code through, a second job without the
guard - the acceptance lapses with it and signing must move to a runner that
never executes candidate code.

**Defence in depth, once public.** `PUT /repos/quadseven/muster/actions/permissions/fork-pr-contributor-approval`
rejects a private repository outright (HTTP 422), so it can only be set after
the flip. Set it to require approval for all outside collaborators. It is a
second lock on a door the condition above already bolts, not a substitute for
it: approval is a human reading a build graph, which is not a thing a human can
reliably audit.

## The ceremony (performed 2026-08-23)

**1. Generate it.** `keytool` prompts for the password twice. Do NOT pass
`-storepass` on the command line, where any local process can read it from `ps`.
PKCS12 uses one password for both the store and the key.

```sh
keytool -genkeypair -v \
  -keystore muster-agent-release.jks \
  -storetype PKCS12 \
  -alias muster-agent \
  -keyalg RSA -keysize 2048 \
  -validity 10000 \
  -dname "CN=muster agent, O=muster, C=US"
```

`-keysize 2048`, not 4096: it matches Google's upload-key guidance, and a
base64 4096-bit PKCS12 runs past the 4096-character ceiling on a standard-tier
SSM parameter. `-validity 10000` is about 27 years - a certificate that expires
while the app is installed is a dead upgrade path.

**2. Back it up before it signs anything.** The password into 1Password, the
`.jks` somewhere that outlives this laptop. This is the step that cannot be
redone.

**3. Into SSM, on the shared CMK `alias/pulumi-secrets`.** That key already
exists and is already paid for; KMS bills per key, not per parameter, so the
only new cost is requests at $0.03/10,000. What it buys for a signing key is a
revocation lever and per-key CloudTrail attribution.

```sh
KSB64=$(mktemp); chmod 600 "$KSB64"
# `| tr -d '\n'` is NOT optional - base64 ends with a newline, file:// stores
# bytes verbatim, and a trailing newline in a keystore is tolerated by some
# decoders and not others. It bit zippie's ceremony on 2026-08-11.
base64 -i muster-agent-release.jks | tr -d '\n' > "$KSB64"
aws ssm put-parameter --type SecureString --key-id alias/pulumi-secrets \
  --name /infra/muster/agent_keystore/keystore_base64 --value "file://$KSB64"
rm -f "$KSB64"

aws ssm put-parameter --type String \
  --name /infra/muster/agent_keystore/key_alias --value muster-agent

# Passwords through a 0600 temp file, never --value "$PW": on put-parameter the
# value is an ARGUMENT, and argv is readable via ps for the life of the call.
#
# `printf` then a BARE `read -rs`. `read -rs -p '...'` works in bash and
# silently does nothing in zsh, where -p means "read from the coprocess". The
# shell here is zsh.
PWF=$(mktemp); chmod 600 "$PWF"
printf 'keystore password: '
read -rs PW; echo
printf '%s' "$PW" > "$PWF"; unset PW

# Prove the password opens the keystore BEFORE storing it. A typo is otherwise
# invisible until a release build fails, long after the terminal that knew the
# real password is gone.
if [ ! -s "$PWF" ]; then
  echo "password was empty - nothing written"; rm -f "$PWF"
elif ! keytool -list -keystore muster-agent-release.jks \
        -storepass:file "$PWF" >/dev/null 2>&1; then
  echo "that password does not open the keystore - nothing written"; rm -f "$PWF"
else
  aws ssm put-parameter --type SecureString --key-id alias/pulumi-secrets \
    --name /infra/muster/agent_keystore/store_password --value "file://$PWF"
  aws ssm put-parameter --type SecureString --key-id alias/pulumi-secrets \
    --name /infra/muster/agent_keystore/key_password --value "file://$PWF"
  rm -f "$PWF"
fi
```

**Read values back with `--output json`, never `--output text`.** Text output
appends a trailing newline, so round-tripping grows the stored value one byte
per pass. That corrupted a parameter in zippie's estate and was caught only by a
digest comparison.

**4. Pin the certificate digest - BEFORE the key is usable by CI.** The order
matters and is not cosmetic.

```sh
# Read it off the keystore itself, not out of a build.
keytool -list -v -keystore muster-agent-release.jks -alias muster-agent \
  | sed -n 's/.*SHA256: *//p' | head -1 | tr -d ': ' | tr 'A-F' 'a-f'

gh variable set MUSTER_RELEASE_CERT_SHA256 -R quadseven/muster --body '<that digest>'
```

**Why before, and not after.** The obvious sequence is to let the first signed
build through and copy the digest it prints. That authenticates nothing: the pin
would be derived from whatever CI happened to sign with, so a mis-seeded or
substituted keystore would be published first and legitimized afterwards by
copying its own digest. The pin has to come from the keystore in your hands,
while you still know it is the one you generated in step 1.

`check.agent-android.yml` enforces the ordering: a release-signed build with no
pin set is a hard failure, not a warning.

**Note on when signing happens.** Only a **push to `main`** receives the signing
secrets. Not pull requests, and not `workflow_dispatch` - a dispatch can select
any branch, and that branch's Gradle wrapper would run with the key on disk,
around review and branch protection. Everything except a main push builds debug
and unsigned. So the release APK appears on the next main build after step 5,
never on the PR or dispatch that preceded it.

**5. Seed the four repo secrets from SSM**, piped so no value touches disk or an
argument list:

```sh
for pair in \
  "MUSTER_KEYSTORE_BASE64:keystore_base64" \
  "MUSTER_KEYSTORE_PASSWORD:store_password" \
  "MUSTER_KEY_ALIAS:key_alias" \
  "MUSTER_KEY_PASSWORD:key_password"
do
  secret="${pair%%:*}"; param="${pair##*:}"
  aws ssm get-parameter --name "/infra/muster/agent_keystore/$param" \
      --with-decryption --output json \
    | python3 -c 'import json,sys; sys.stdout.write(json.load(sys.stdin)["Parameter"]["Value"])' \
    | gh secret set "$secret" -R quadseven/muster
done
gh secret list -R quadseven/muster
```

**6. Record the certificate checksum.** This is the value that goes into every
QR, so it belongs in `docs/what-is-deployed.md`:

```sh
# From the release APK once CI has built one:
cd server && uv run --group dev python -c \
  "from muster import provisioning; print(provisioning.signature_checksum('app-release.apk'))"
```

## What CI does with these

**Added 2026-08-23, and it did not exist when this document was written.**
`check.agent-android.yml` decodes `MUSTER_KEYSTORE_BASE64` into `RUNNER_TEMP`,
exports `MUSTER_KEYSTORE_PATH`, and runs `assembleRelease` instead of
`assembleDebug`. Before that step existed, every instruction above could be
followed exactly and the next build would still be debug-signed - the key
generated, backed up, stored under the shared CMK and seeded into GitHub, with
not one byte of it reaching a build. The ceremony would have completed, reported
success, and prevented nothing.

A `Prove it is not debug-signed` step now reads the certificate back out of the
built APK and fails on `CN=Android Debug`, so the same gap cannot reopen
silently. It checks the subject rather than a pinned digest because the SDK's
debug keystore is per machine.

## What the build already does with these

`agent/android/app/build.gradle.kts` reads `MUSTER_KEYSTORE_PATH`,
`MUSTER_KEYSTORE_PASSWORD`, `MUSTER_KEY_ALIAS` and `MUSTER_KEY_PASSWORD`. With
none of them set it builds debug exactly as before, so unit tests need no key
anywhere near them. Three behaviours are worth knowing:

- **A keystore path inside the checkout is refused.** A keystore in the tree is
  one that leaks with the tree.
- **Half-seeded secrets fail loudly.** A path with no password produces a clear
  error rather than an APK signed by something other than what you think.
- **`packageRelease` without a key is a RED build.** AGP treats an unsigned
  release APK as a normal output - `app-release-unsigned.apk` - which no phone
  installs. A green build producing an unusable artifact is worse than a
  failure.

**v1 (JAR) signing is pinned on for release**, which is where muster diverges
from the zippie companion. apksigner chooses schemes by minSdk, and at 29 it
signs v2/v3 and skips v1 - but muster reads the signing certificate out of the
v1 PKCS#7 block in `META-INF`, so a v2-only APK has a certificate this cannot
read. The build would stay green and the APK could never provision anything.
`build.server-image.yml` also reads the certificate out of the baked APK and
fails if it cannot, so this is caught twice.
